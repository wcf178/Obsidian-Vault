## 2. 事务的隔离级别

### 2.1 读未提交

允许读取未提交的事务。

**脏读示例：**

1. 事务 A 更新了 `stock` 字段为 `stock + 1`，但是还未提交。
2. 事务 B 读取了这条记录的 `stock` 字段，得到了 `stock + 1` 的结果。
3. 事务 A 后续出现问题，进行了回滚。

这就导致事务 B 读取到了错误的数据，即**脏读**。

### 2.2 读已提交

允许读取已提交的事务。

**不可重复读示例：**

假设 `stock = 1`，以下事务执行顺序可能会出现不可重复读的问题：

| 顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | 开始 | — |
| 2 | — | 开始 |
| 3 | — | 读取 `stock`，得到 `stock = 1` |
| 4 | 更新 `stock = stock + 1` | — |
| 5 | 提交 | — |
| 6 | — | 读取 `stock`，得到 `stock = 2` |

事务 B 中两次读取得到的值不同，这就是**不可重复读**的问题。

### 2.3 可重复读

可能会出现**幻读**的问题。

### 2.4 串行化

读取事务和更新事务都是阻塞的，一个事务完成之后才允许下一个事务继续执行。

## 3. 事务隔离性的实现

事务的隔离性实现依靠**锁**和 **MVCC 机制**。

## 4. 可重复读的实现原理：MVCC

### 4.1 隐藏字段与版本更新

1. 一条记录包括两个隐藏字段：
   - `DB_TRX_ID`：事务 ID。
   - `DB_ROLL_PTR`：指向 undo log 中该行上一个版本的指针。
2. 当行记录被修改的时候，旧版本的数据会写入 undo log，这个更新记为事务 B。
3. 当前行的 `trx_id` 会更新为这个事务的 ID。

### 4.2 Read View 的关键信息

在第二步骤之前启动的事务 A 中读取这条行记录的时候，事务 A 会创建一个 **Read View（RV）**，其中包括几个关键的信息：

| 字段 | 含义 |
| --- | --- |
| `creator_trx_id` | 当前事务 A 自己的 ID |
| `max_trx_id` | 下一个将要分配的事务 ID |
| `min_trx_id` | 活跃事务里最小的 ID |
| `m_ids` | 创建 RV 的时候依然活跃、未提交的事务 ID |

### 4.3 版本可见性判断

接下来事务 A 读取的时候就会判断：

| 判断条件 | 说明 | 可见性 |
| --- | --- | --- |
| `DB_TRX_ID == creator_trx_id` | 这条记录是自己刚刚修改的 | 可见 |
| `DB_TRX_ID < min_trx_id` | 这条行记录最后的更新在 RV 创建前就已经提交 | 可见 |
| `DB_TRX_ID >= max_trx_id` | RV 创建之后这条行记录进行了修改并提交了 | 不可见 |
| `DB_TRX_ID` 在活跃的事务列表中 | 未提交 | 不可见 |
| 其他情况 | 已提交 | 可见 |

如果不可见，则顺着 `DB_ROLL_PTR` 找 undo log 中的旧版本，继续判断。

## 5. 可重复读与幻读

可重复读的幻读问题在 InnoDB 中解决了。

**幻读**是指：在范围查询的时候，其他事务插入的记录会被第二次范围查询获取到，出现同一个 SQL 语句查询到了不一样的记录。

- **快照读**：InnoDB 的 MVCC 机制中，RV 中不存在后续插入的记录，因此不会导致幻读。
- **当前读（非快照读）**：MySQL 采用间隙锁来锁住记录之间的间隙，阻塞其他事务在事务内插入新行。

## 6. 可重复读的脏写问题与解决方式

可重复读的隔离级别会出现脏写的问题。比如在上面的事务中，事务 A 读取到了过往版本的数据，然后根据这个旧数据做了运算，得到了一个错误的数据，更新上去后就会覆盖事务 B 已更新的数据。

那么如何解决这个脏写的问题？

### 6.1 悲观锁

**先加锁，然后再操作。**

在读取数据的时候，通过 `SELECT ... FOR UPDATE` 对行加排他锁。其原理是阻塞其他事务对同一行的写操作或者加锁读，强制它们等待，直到当前事务提交或者回滚。

> [!warning] 注意
> - 悲观锁的 `SELECT ... FOR UPDATE` 必须走索引，否则可能会升级为表锁，影响并发性能。
> - 还需要控制事务长度。

### 6.2 乐观锁

在表后面加 `version` 字段。更新的时候加上 `version` 条件过滤，如果影响行数为 `0`，则说明发生冲突。

```sql
UPDATE inventory
SET stock = new_stock,
    version = version + 1
WHERE id = 1
  AND version = <old_version>;
```

### 6.3 原子更新

```sql
UPDATE inventory
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;
```

数据库在执行的时候会自动加锁，保证**检查条件**和**执行更新**的原子性。

## 7. 查询操作需要添加事务吗？

在 RR 的情况下，某些业务场景下需要进行事务。

比如在**报表导出**时，需要分多批查询数据。如果查询不加事务，中间可能会有事务执行更新，导致：

- 一开始查询读取的是旧数据。
- 后面查询读取的是最新数据。

这会导致数据不一致，不是同一个时间点的数据。

## 8. 隔离级别的选择

- **高并发**：用 RC。
- **报表多、并发不多**：用 RR。
