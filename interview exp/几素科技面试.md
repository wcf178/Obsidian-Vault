## 第一题：你们的代码是怎么发布的？

难度：简单 · 考察 CI/CD 实践

### 面试推荐回答

> 我们项目早期的发布流程比较简单，开发完成之后，直接把代码部署到线上服务器。
> 
> 后来随着项目规模扩大，团队逐步规范发布流程，改成了基于 GitLab CI/CD 的自动化部署。

这里的流水线步骤是一个标准示例，具体有没有自动执行 Composer、数据库迁移或测试，要以你原项目真实流程为准。

### 技术知识补充：Eloquent 访问器

Laravel 5.6 常见写法：

```
public function getFullNameAttribute($value)
{
    return strtoupper($value);
}
```

Laravel 9 新增的写法：

```
use Illuminate\Database\Eloquent\Casts\Attribute;

{
    return Attribute::make(
        get: fn ($value) => strtoupper($value),
    );
}
```

新版本可以通过 `Attribute` 对象组织访问器和修改器逻辑。不过 Laravel 9 仍然支持传统访问器写法，并不是必须全部迁移。

### 面试官可能追问

Q：适配器模式和工厂模式有什么区别？

> 适配器模式解决接口不兼容的问题，工厂模式负责创建或选择对象。
> 
> 在多平台系统中，工厂根据平台标识找到对应适配器，适配器负责处理平台接口差异。

Q：如果平台有很多特殊字段，统一接口还能适配吗？

> 可以把公共流程统一，把平台差异保留在适配器内部。对于平台特殊能力，可以定义可选能力接口或独立策略，而不是强行要求所有平台完全一致。

## 第五题：不同平台的商品 Schema 不一样，怎么适配成统一的数据结构入库？

核心架构题 · 最值得深入准备

这是面试官在第 4 题之后继续追问的问题。

从提问方式来看，他其实想考察你有没有数据建模能力、系统抽象能力和多平台业务理解能力。

### 面试推荐回答

> 如果需要同时对接 Walmart、Temu、TikTok Shop 等多个电商平台，我会采用统一数据模型加适配器的设计方式。
> 
> 首先，在数据库层面抽象出各个平台共有的商品字段，比如商品标题、SKU、价格、库存、商品状态、所属平台和站点等。
> 
> 其次，在业务层面定义统一的商品数据结构，由不同的平台适配器负责字段映射和数据转换。
> 
> 比如 Walmart 可能返回 `sku`、`productName`，而另一个平台可能返回 `seller_sku`、`title`。虽然字段名称不一样，但表达的是相似的业务含义，我们可以把它们转换成统一的 `sku` 和 `name`。
> 
> 对于各平台特有的属性，比如类目专属字段、商品认证信息等，我不会强行放到统一主表里，而是考虑使用 JSON 扩展字段或者平台扩展表保存。
> 
> 同时，还要考虑平台和站点之间的差异。比如 Walmart 不同站点的数据 Schema 可能不同，可以根据平台、站点、类目和 Schema 版本选择对应的映射规则。
> 
> 最后，在入库时，可以通过平台、站点、店铺和平台商品 ID 建立唯一标识，使用 Upsert 或者其他幂等机制避免重复数据。
> 
> 这样既能保证核心数据结构统一，又能保留不同平台的业务差异，后续增加新平台也比较容易扩展。

这段回答的关键是：统一的不是所有原始字段，而是各平台共有的业务语义。

### Laravel 示例：实现统一字段转换

```
interface ProductAdapterInterface
{
    public function normalize(array $data): array;
}

class WalmartProductAdapter implements ProductAdapterInterface
{
    public function normalize(array $data): array
    {
        return [
            'sku'      => $data['sku'],
            'name'     => $data['productName'],
            'price'    => $data['price']['amount'],
            'currency' => $data['price']['currency'],
            'stock'    => $data['availability']['quantity'],
        ];
    }
}

class TikTokProductAdapter implements ProductAdapterInterface
{
    public function normalize(array $data): array
    {
        return [
            'sku'      => $data['seller_sku'],
            'name'     => $data['title'],
            'price'    => $data['sale_price'],
            'currency' => $data['currency'],
            'stock'    => $data['stock'],
        ];
    }
}
```

示例省略了字段缺失校验、异常处理和原始响应保存。生产环境中不能直接假设字段一定存在。

### 面试官可能追问

Q1：如果同个平台不同站点的 Schema 也不一样呢？

> 我会进一步把平台适配和站点映射拆开。平台适配器处理基础 API 协议，站点或类目映射规则处理字段差异。
> 
> 对于变化频繁的 Schema，可以考虑将映射规则配置化，并记录 Schema 版本，方便适配后续平台变更。

Q2：商品特有字段有几百个，难道全部放进数据库吗？

> 不会全部塞进商品主表。常用公共字段单独建列，方便查询和索引；平台专有字段可以使用 JSON 或独立扩展表；对于需要高频筛选的属性，再考虑拆分成结构化字段。

Q3：如果 Walmart 和 Temu 的同一款商品有不同 SKU，怎么关联？

> 不能简单依靠平台 SKU 判断是否属于同一个内部商品。可以通过本地 SKU、商品编码或人工维护的映射关系，把不同平台的 Listing 关联到统一的内部商品及变体。

Q4：如果接口同步失败或者返回的数据不合法怎么办？

> 不会直接写入错误数据。可以保存原始响应和错误原因，记录同步任务状态，将失败任务放入有限重试流程。对于长期失败的数据，提供异常记录和人工排查入口。

## 第六题：简单介绍一下你的订单对接系统

你的项目优势 · 必须讲熟

这道题你原来的回答方向没有问题，但是略微简单。

面试官问你介绍项目时，建议按照：

业务背景 → 核心流程 → 技术难点 → 个人职责

这样的顺序来回答。

### 面试推荐回答

> 我参与的订单对接系统主要负责把前端销售系统的订单同步到进销存系统，再由进销存系统完成库存处理和后续发货流程。
> 
> 首先，订单产生之后，上游系统会通过 RabbitMQ 发送订单消息，我们的系统作为消费者接收订单数据。
> 
> 接收到消息之后，会进行订单数据解析、业务校验以及订单处理。
> 
> 在库存方面，我们会结合 MySQL 和 Redis 处理库存相关业务，同时通过 Redis 锁避免同一订单被并发重复处理。
> 
> 订单确认可以正常处理后，会根据业务规则调用第三方海外仓接口创建出库单或发货单。
> 
> 海外仓完成相应操作后，系统还需要同步发货状态、物流单号等信息，保证本地订单状态和第三方仓储系统尽量一致。
> 
> 另外，因为订单系统涉及消息队列以及第三方接口调用，所以还需要考虑重复消息、处理失败以及状态同步异常的问题。
> 
> 我们在消息处理方面采用了 ACK 机制，并通过定时任务进行业务数据校验，作为异常情况下的兜底措施。

### 面试官可能追问

Q1：订单消息重复消费怎么办？

Q2：库存扣减失败怎么办？

> 
> 如果库存服务是独立系统，就需要通过订单状态、重试和补偿机制处理，而不是依赖一个跨系统数据库事务。

Q3：调用海外仓接口超时，但是对方实际上已经创建了发货单，怎么办？

这是一个很典型的分布式系统问题。

推荐回答：

> 不能因为接口超时就直接认为创建失败。
> 
> 我会优先使用唯一业务单号或者第三方提供的幂等请求标识。如果接口超时，先查询海外仓是否已经存在对应的出库单。
> 
> 如果已经存在，就同步对应结果；如果确定不存在，再考虑重试。
> 
> 对于无法立即判断的情况，可以先标记为待确认状态，交给定时任务补偿，避免重复创建出库单。

这道追问非常值得你掌握。 它能很好地体现你理解分布式业务，而不仅仅是会调用第三方 API。

## 第七题：RabbitMQ 消息丢失怎么处理？怎么监听和解决？

本次重要失分点 · 高频面试题

这道题我建议你重点准备，因为它既考察消息队列的知识，也能结合你实际做过的订单业务回答。

### 面试推荐回答

> RabbitMQ 的消息可靠性，我会从生产者、RabbitMQ Broker、消费者以及业务补偿四个方面考虑。
> 
> 先说我们实际的业务。我们主要使用 RabbitMQ 传递订单消息，消费端在收到消息之后，会先执行订单处理逻辑，处理完成后才返回 ACK，避免消息还没有处理完就被确认。
> 
> 另外，我们还有一个业务兜底机制，通过定时任务校验上下游订单数据的一致性。如果发现订单没有被正常处理，就进行异常排查和补偿。
> 
> 如果从完整的 RabbitMQ 可靠性方案考虑，生产者端可以开启 Publisher Confirm，确认消息是否成功到达 Broker；同时使用 mandatory 和 Return 机制处理消息无法路由到队列的情况。
> 
> Broker 端可以使用持久化队列和持久化消息，降低服务重启造成消息丢失的风险，对于可靠性要求较高的订单消息，也可以考虑 Quorum Queue。
> 
> 消费者端采用手动 ACK，业务处理成功后才确认消息。如果发生临时异常，可以按照重试策略重新处理；如果多次失败，则可以进入死信队列，避免一直重复消费。
> 
> 最后，因为 RabbitMQ 在异常重试过程中可能产生重复投递，所以消费者必须保证幂等性，比如通过订单唯一标识和数据库状态校验，防止重复扣库存。
> 
> 总体上就是通过消息确认、持久化、失败重试、业务幂等和定时补偿，尽量保证订单消息不丢失、业务不重复执行。

### 技术知识补充

RabbitMQ 的可靠性需要分阶段考虑：

|环节|可能的问题|解决方案|
|---|---|---|
|生产者|消息发送失败|Publisher Confirm、失败重试|
|路由|找不到目标队列|mandatory + Return|
|Broker|宕机导致消息丢失|持久化、Quorum Queue|
|消费者|业务还没处理就确认|手动 ACK|
|消费者|消费失败|有限重试、死信队列|
|业务层|消息重复投递|幂等处理|
|业务层|漏单或状态异常|定时对账、补偿|

要特别注意，Publisher Confirm 只能证明 Broker 已经按相应机制接收消息，并不代表消费者已经完成业务处理。

### 面试官可能追问

Q1：如果消费者正在扣库存，服务突然挂了怎么办？

> 如果使用手动 ACK，消息还没有确认，RabbitMQ 在检测到消费者连接或通道关闭后，会重新投递未确认的消息。
> 
> 但是如果数据库扣库存已经提交，ACK 还没发出去，消息就可能被重复消费，所以还需要业务幂等。

Q2：ACK 和 NACK 有什么区别？

> ACK 表示消费者已经完成处理，RabbitMQ 可以把这条消息标记为已确认。
> 
> NACK 表示拒绝当前消息，可以选择是否重新入队。
> 
> 对于业务异常，我不会无条件重新入队，因为持续失败的消息可能导致无限重试。

Q3：怎么监听消息丢失？

> RabbitMQ 自身不能直接判断业务系统有没有漏掉某个订单。
> 
> 在消息层可以监控 Publisher Confirm 失败、Return、队列积压、未确认消息数量、消费者异常和死信队列。
> 
> 在业务层还需要通过订单唯一 ID 和上下游订单状态对账，发现未同步或者长时间未完成处理的订单，再触发告警和补偿。

这很可能是面试官第 7 题真正想听到的部分：怎么发现问题，以及发现后怎么恢复，而不仅仅是如何 ACK。

Q4：如果生产者发送消息成功，但消费者没有收到，怎么处理？

> 先通过消息发布确认、路由和队列监控判断消息进入了哪个阶段。
> 
> 如果消息已经入队，可以检查消费者状态、消息积压、未确认消息和死信队列。
> 
> 如果业务侧长时间没有对应订单记录，则通过定时对账发现并补偿。对于需要防止数据库提交成功但消息未发送的场景，还可以考虑 Outbox 模式。

## 第八题：Redis 主要使用在哪些业务场景？

你的实际经验 · 继续完善细节

### 面试推荐回答

> Redis 在我们的项目中主要用在两个场景，一个是防止同一业务重复并发执行，另一个是库存数据缓存。
> 
> 第一是订单处理的并发控制。
> 
> 因为订单通过消息队列异步处理，可能出现同一个订单被重复投递，或者同一时间有多个任务处理同一订单的情况。
> 
> 这个时候可以使用 Redis 分布式锁，以订单 ID 作为锁的业务标识，避免多个消费者同时处理同一个订单。
> 
> 但是 Redis 锁只能控制并发，不能完全代替幂等判断，所以还需要结合数据库唯一索引和订单状态，确保重复消费不会重复扣库存。
> 
> 第二是库存缓存。
> 
> 因为库存数据读取频率比较高，如果每次都查询 MySQL，会给数据库带来压力，所以我们会把部分库存数据缓存到 Redis 中，提高读取性能。
> 
> 不过库存属于比较敏感的数据，Redis 和 MySQL 之间可能存在数据不一致的问题，所以需要明确库存更新策略，保证关键扣减逻辑的正确性。
> 
> 整体而言，Redis 主要帮助我们优化并发控制和数据读取性能。

### 技术知识补充：Redis 分布式锁

假设有两条相同订单消息同时进入消费者：

消费者 A

成功获得锁

进入订单处理逻辑

消费者 B

未获得锁

稍后重试或等待

Redis 分布式锁

order:lock:10001

MySQL 订单状态与唯一约束

最终校验是否已经完成处理

在 Laravel 9 中，如果使用支持原子锁的 Redis 缓存驱动，可以通过 Cache Lock 实现：

```
use Illuminate\Support\Facades\Cache;

$orderId = 10001;

$lock = Cache::lock("order:lock:{$orderId}", 30);

if (!$lock->get()) {
    // 没拿到锁：应重试或延迟处理
    return;
}

try {
    // 获取订单状态
    // 判断是否已经处理过
    // 执行需要保护的业务操作
    // 更新处理结果
} finally {
    $lock->release();
}
```

这里的代码只是演示锁的使用方式，真实队列消费者不能因为没拿到锁就直接确认消息处理成功。

如果没拿到锁，需要根据业务安排重试或延迟处理。另外，锁租期必须覆盖受保护操作的执行时间，长任务可能需要续期或其他防并发设计。

### 面试官可能追问

Q1：Redis 分布式锁怎么实现？

> 通常可以使用 `SET key value NX EX seconds`，实现原子性的加锁和过期时间设置。
> 
> `NX` 保证只有 Key 不存在的时候才能设置成功，`EX` 用于设置超时时间。
> 
> 解锁时要验证锁的持有者，不能直接 `DEL`，可以使用 Lua 脚本执行比较并删除，或者使用支持所有者令牌的成熟锁组件。
   qq
Q2：为什么还要设置锁的过期时间？

> 如果服务执行过程中异常退出，没有正常释放锁，过期时间可以避免锁永久存在。
> 
> 但要注意，如果业务执行时间超过锁的有效期，就可能出现锁提前释放，其他消费者进入临界区的问题。

Q3：Redis 库存和 MySQL 库存不一致怎么办？

> 首先要明确谁是权威数据源。
> 
> 如果 MySQL 作为最终库存数据源，Redis 主要用于加速读取，可以在数据库更新成功后删除缓存，并在读取时重新加载。
> 
> 如果 Redis 用于高并发库存预扣减，则需要另外设计 Redis 与数据库之间的异步落库、失败补偿和库存对账机制。
> 
> 不管采用哪种方式，都不能仅仅因为 Redis 显示有库存，就认为最终一定能够完成扣减。

Q4：如果两个不同订单同时扣同一个 SKU 的库存，Redis 订单锁能防止超卖吗？

> 不能。
> 
> 因为按照订单 ID 加锁，只能避免相同订单的并发处理，无法限制不同订单对同一个 SKU 的竞争。
> 
> 对库存扣减，可以在 MySQL 中使用条件更新，比如 `UPDATE ... SET stock = stock - 1 WHERE sku = ? AND stock >= 1`，通过影响行数判断扣减是否成功。
> 
> 在高并发场景下，也可以考虑 Redis 原子预扣库存，再通过可靠的异步流程落库和补偿。

这是一道比较有区分度的追问。答出订单幂等和库存防超卖是两个不同问题，会比单纯说 Redis 加锁更好。
